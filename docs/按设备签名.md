# Per-device ROM signing (按设备签名)

One bad actor must not poison every device. VineOS ROMs are therefore
licensed **per device**: the server signs a license binding
(device, ROM hash) with an offline Ed25519 root key, and the app
refuses to boot anything else once a root key is configured.
Revoking one device affects exactly that device.

## Threat model

- A malicious user repacks a `.vrom` with spyware and redistributes it.
  Without per-device licenses, every downloader would trust it.
  With licenses, the repacked file's hash no longer matches any
  victim device's license, so victims' apps refuse to boot it.
- A malicious device exfiltrates its own licensed ROM. The operator
  revokes that one device ID; all other licenses keep working.
- Server compromise is out of scope: the root key lives offline and
  only signs licenses and the revocation list.

## Flows

1. **Enroll**: the app generates an Ed25519 device keypair
   (`安全/设备密钥管理器`), `device_id = sha256(pubkey)`.
   The device sends `(device_id, pubkey)` to the operator out of band.
2. **Issue**: the operator runs `scripts/按设备签名ROM.py 签发`
   with the offline root key. Output `<rom>.<device>.license.json`
   travels with the `.vrom` (sidecar) or via `licenseUrl`.
3. **Verify** (every boot, `安全/许可证门禁` in `VineVMManager`):
   root signature valid → package hash matches → not expired →
   device matches → device not revoked. Any failure = `ERROR`,
   with the reason recorded in the launch-path log.
4. **Revoke**: `scripts/吊销管理.py 吊销` re-signs the revocation
   list; the app syncs it (`安全/吊销同步器`) and enforces from cache.

## Server setup

```bash
# One-time, on an offline machine. NEVER commit the root key.
python3 scripts/设备密钥生成.py 生成根密钥 --输出 /secure/根密钥.json
# The public half goes into release builds:
#   ./gradlew assembleRelease -PromCaPubkeyHex=<根公钥hex>
```

Dev/CI builds ship with an empty key on purpose: the gate stays
open so development and CI are unaffected. Release builds MUST
inject the key, otherwise licenses are not enforced.

## ROM builds (the honest part)

Real `system.img`/`vendor.img`/`ramdisk.img`/`kernel` binaries can
only be produced from AOSP on a Linux host (see `docs/BUILDING.md`
and `scripts/build_rom.sh`). That is what
`.github/workflows/build-rom.yml` does on GitHub runners
(`workflow_dispatch`, matrix 7/9/11/12): build → package `.vrom` →
emit test licenses signed by an ephemeral CI key → upload artifacts.
Production licenses are issued separately with the offline root key;
CI never sees it.
